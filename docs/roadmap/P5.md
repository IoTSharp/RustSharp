# P5: Acceptance-sized database and ORM tasks

English | [简体中文](P5_zh.md) | [Back to roadmap](../../ROADMAP.md)

This list decomposes the existing P5 scope without expanding compatibility promises. Every leaf is ⏳ Planned; implementation directories, profiles, manifests, runners and reports below are planned deliverables, not existing execution evidence. A parent completes only when all its leaves pass. Aggregate node `P5-GATE` requires P5-01 through P5-06 and all four gate leaves. P5-07 retains its original post-P5 evaluation scope and is **outside the P5 exit-blocking set**; it promises no diesel support. This removes the gate dependency cycle without reducing database delivery scope.

The first leaf of each parent inherits its hard prerequisites from the main roadmap; later leaves inherit them transitively through the listed edges. Parent IDs such as `P2-06` mean all their leaves; nodes such as `P3-GATE` mean the whole phase gate. File/directory ownership is limited to the stated unit; shared interface or manifest changes must be coordinated serially, even when other directories differ.

An evidence key `suite-v1#group` denotes the planned `tests/roadmap/suite-v1.json` and its named group. Each manifest must enumerate immutable case IDs, input hashes, expected outcomes, positive/negative/boundary/budget classification and an exact denominator. `tools/RustSharp.Conformance` is to gain `--manifest <path> --group <group>`; this future entry point is not a currently executable command. The deliverable column bounds the accompanying test directories. Local reports are planned at `artifacts/p5/local/<suite>/<group>.json`; native CI uploads equivalent reports with stable run and artifact links. Ignored artifacts need not be committed. Decision leaves freeze versions and numeric budgets first. Extensions add a new manifest version; they never delete, relax or replace existing cases or adjust denominators at closure.

Every report records compiler SHA, tool/provider/server versions, profile, lock hash, platform/RID, command, denominator, failure reasons, timeout, maximum attempts/backoff, PID/parent PID/start time and cleanup outcome. Runners support cancellation, numeric resource caps and owned-resource-only cleanup. Database unavailability is blocked evidence, never a skip or pass. Functional leaves require corresponding positive, negative, boundary and budget evidence. Local and CI passes are recorded separately, and every declared runtime cell actually executes.
